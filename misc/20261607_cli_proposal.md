# LifeCore CLI Proposal

An intuitive CLI interface to common database operations that makes correct
usage of the API.

Features:

- Store database on disk in JSON format
- Event alias
- Batch operations via TOML "sidecars"
- Apply Suggestions - Query by node type, present field name, event range, regex
  over payload
- Helpful `InteractiveAnalyzer` to aid in interactive usage
- Barklist
- Query Command
- GraphViz SVG output, with and without ancestors

These features are described in this document.

# Mode Of Operation

The purposed mode of operation for adding an alias or updating an alias or
applying a suggestion or adding a diagnostic to the barklist is as follows:

- User invokes the CLI for the aforementioned operation, and receives a numbered
  list of possible targets from the CLI.
- The user re-invokes the CLI with `--select X` to select an entry from the
  previous table, CLI performs the aformentioned operation on the selected item.
  - Note that to facilitate interactions of this sort, the order of output
    entries needs to be deterministic! This requires a review of the internal
    API and especially the diagnostics handling, plus sorting the results.

# Storage

By default, the CLI should operate on the database from a JSON file in the
current directory named `LifeCoreDB.json` UNLESS environment variable
`LIFECORE_DB_PATH` is defined; then the database path is the path that is
specified by the environment variable. In this mode CLI SHALL NOT fall back to
the implicit working directory path in case of errors (e.g. path specified in
the environment variable is non-existant)

Before the database is usable, it must be initialized via an `init` subcommand.
Then, the database path derived from the procedure above is created with no
initial events contained. `init` fails if the database file already exists.

`init` shall run Basic Validation and the analyzers on the empty database.

# Alias

CLI should store separate CLI-related information alongside the actual database
in the database file. One piece of information that is stored is the
user-defined string aliases to absolute `PointedEventContext`.

Users cannot construct or specify `PointedEventContext` directly on the
commandline; instead they can alias values that are generated by a query or an
insertion operations.

Aliases and what they refer to can be viewed via `alias list` subcommand. If the
node referred to by the alias has been overridden, users are given the option to
update the alias to point to any of the fresh successors.

`alias remove <name>` to forget an alias.

Multiple aliases SHALL NOT refer to the same event. i.e. `PointedContext`s must
form a set with the same number of elements as the aliases.

Alias names are unique. As long as an alias exists, users may not add another
alias of the same name.

# Sidecar

To further ease the use of LifeCore, the user may specify any number of
operations in a separate file, dubbed "a sidecar" from here on out. You can
think of the sidecar as an extension of the main database, describing enteries
to be added.

An alias may not be added after a sidecar is attached. List of aliases are
cleared when a sidecar is committed and written into the main database.

Sidecar entries are inserted in the memory-resident representation of the
database, without writing to the main database file by default, with validation
and analyzers run at each turn just like singular insertions in normal
operation.

A sidecar may be attached with a dedicated subcommand
`sidecar attach <filename>`. It may be committed or detached similarly.

## Format of The Sidecar

Sidecars are regular TOML files, with special rules for converting between TOML
values and `PayloadExt`.

Sidecar enteries are stored in an array of TOML tables located in the root
table. Each array entry contains a number of fields describing the entry. Here
is a sample:

```toml
[[entry]]
alias = "BuyMilk"
ty = "Note"
[entry.body]
content = "Buy Milk"
[entry.connect]
from = [
    { target = "AtWork", ty = "Related" }
]
to = [
    { target = "DairyContrib", ty = "Accumulate" }
]
```

Sidecar entries describe a new node, and how it shall be connected to the rest
of the graph. The sample results in the following changes to the database:

- A new node of type "Note" is inserted, with a single string PayloadExt
  corresponding to the field `content`.
- Edges in `from` are added in the order of iteration. (in the order that they
  appear in the deserialized table)
- Edges in `to` are added in the order of iteration. (in the order that they
  appear in the deserialized table)

An alias "BuyMilk" is added after the entry is fully processed.

Sidecars may refer to aliases already introduced before attaching the sidecar.

Rules for converting TOML values to PayloadExt are not settled on right now, and
the only mandatory functionality for now is converting integers and strings to
PayloadExt variants. The implementation must be flexible enough for adding
future rules regarding Timestamp and Serialized and new PayloadExt types.

# InteractiveAnalyzer

For the lastest added node, if the node has a parent, consider the edges of the
parent and suggest to recreate the connections if the other end of the edge is
not stale AND any fresh siblings or the node itself don't already have a similar
connection. Applicable only for the latest added node in the analysis window.
